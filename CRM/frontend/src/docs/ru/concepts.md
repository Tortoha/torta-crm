# Концепции

Несколько идей, которые применимы к каждому вызову `torta-js`. Прочитайте это один раз — и остальной справочник станет очевидным.

## Три ключа

| Ключ | Префикс | Где находится | Секретный? |
|------|---------|---------------|------------|
| **Публичный ключ** | — (20 hex-символов) | В пути URL (`/PUBLIC_KEY`) | Нет — безопасен в браузере |
| **Publishable-ключ** | `pk_` | Заголовок `X-Publishable-Key` (SDK добавляет сам) | Нет — безопасен в браузере |
| **Секретный ключ** | `sk_` | Заголовок `X-Secret-Key`, **только сервер** | **Да — никогда не отдавать в браузер** |

Публичный и publishable-ключи использует `createClient(url, pk)`. Publishable-ключ проверяется при каждом запросе, поэтому скопировать один URL недостаточно, чтобы вызвать API.

**Секретный ключ** открывает server-to-server эндпоинты (сейчас это `client.customers.save`). Передавайте его третьим аргументом и только со своего бэкенда:

```js
const client = createClient(url, pk, { secretKey: 'sk_…' }); // ТОЛЬКО СЕРВЕР
```

См. [Приём клиентов](/docs/customers).

## Формат ответа

Каждый метод возвращает один и тот же объект — он никогда не бросает исключение на HTTP-ошибках:

```js
const { ok, status, data, error } = await client.products.list();
```

| Поле | Тип | Значение |
|------|-----|----------|
| `ok` | boolean | `true` при 2xx |
| `status` | number | HTTP-код (`0`, если запрос не ушёл) |
| `data` | object \| array \| null | Распарсенный JSON или `null` |
| `error` | string \| null | Готовое к показу сообщение при ошибке, `null` при успехе |

`error` — всегда **обычная строка**, даже если бэкенд вернул массив ошибок валидации или вложенный объект `{ detail }`: SDK нормализует это за вас. Поэтому строку можно сразу класть в тост:

```js
const r = await client.cart.add(productId, variationId, configId, 1);
if (!r.ok) return toast(r.error);
```

## Сессии и авто-рефреш

Авторизация работает на cookie. После входа браузер хранит httpOnly access-токен (15 минут) и refresh-токен (30 дней). Токенами вы не управляете — когда любой запрос возвращает **401**, SDK тихо вызывает `/refresh` один раз и повторяет запрос. Параллельные 401 разделяют один рефреш, чтобы не было гонки.

Если рефреш тоже не удался, кеш пользователя сбрасывается, а исходный 401 возвращается — это сигнал перенаправить на вход:

```js
const r = await client.orders.list();
if (r.status === 401) redirectToLogin();
```

## CSRF

Запросы, меняющие состояние (POST/PUT/PATCH/DELETE), используют схему double-submit cookie. SDK сам получает cookie `csrf_token` и дублирует её в заголовке `X-CSRF-Token`. Ничего делать не нужно — просто знайте, что самый первый «пишущий» запрос вызывает однократный `GET /csrf`.

## Серверный рендеринг (SSR)

Так как авторизация живёт в cookie браузера, **вызовы от имени пользователя должны выполняться в браузере** (компоненты, `useEffect`, `onMount`). Публичные данные (товары, категории, конфиг) можно загружать и при SSR, ведь `fetch` есть в Node 18+, но сессия пользователя там недоступна. SDK защищает обращения к `window`/`document`, поэтому импортировать его в серверный бандл безопасно — просто будет меньше данных аналитики.

## Никаких сырых fetch

Держите все вызовы API внутри SDK. Он централизует ключи, CSRF, рефреш и нормализацию ошибок в одном месте — сырые `fetch()` в компонентах переписывают всё это заново и со временем расходятся с реальностью.
